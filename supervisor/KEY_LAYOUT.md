# The control plane's key layout

What the control plane writes into the shared key/value store, and what the supervisor may therefore
read. This is the **only** interface between the two services — neither calls the other.

Generated by exercising the control plane at commit `55edd31` and dumping every key it wrote, so the
documents below are real rather than reconstructed. Regenerate it the same way after any change to the
control plane's storage: this file is a contract, and a contract drifts.

## Ground rules

**Keys are opaque strings; values are opaque bytes.** In practice every value here is UTF-8 JSON, but the
store does not know that and neither backend interprets it.

**Every key is prefixed `tenant/<tenant-id>/`, with exactly one exception**: the tenant registry,
`tenants/<tenant-id>`, which lives at the root because it is what you read to learn the tenant ids in
the first place. Single-tenant deployments use the literal tenant `default`. The prefix is applied by a
decorator the control plane wraps its store in, so no handler ever sees it — but the supervisor reads the
*root* store and must include it. A supervisor that forgets the prefix sees an empty store rather than an
error, which is the most likely way to lose an afternoon.

**Every key carries a revision.** Opaque, comparable only for equality, and not meaningful across keys.
Use it for compare-and-set, never for ordering between keys. On etcd it is a cluster-wide counter and does
advance when unrelated keys change; on ZooKeeper it is the modification zxid.

**Writes are per-key.** The control plane has no cross-key transaction and does not want one — a request
that touches an index and its aliases writes two keys, not one atomically. **The supervisor must therefore
tolerate torn state**: an index whose alias is not yet updated, a data stream naming a backing index whose
document has not appeared. This is a design property, not a bug to route around; see the control plane's
README on why aliases are their own resource.

## The layout

| key | written by | holds |
|---|---|---|
| `indices/<name>` | `indices.create`, `put_mapping`, `put_settings`, `open`, `close` | one index's full configuration |
| `aliases/<name>` | the alias operations, and `indices.create` via templates | which indices an alias points at |
| `data_streams/<name>` | `indices.create_data_stream` | a stream's backing indices and generation |
| `templates/index/<name>` | `indices.put_index_template` | a composable index template |
| `templates/component/<name>` | `cluster.put_component_template` | a component template |
| `templates/legacy/<name>` | `indices.put_template` | a legacy template |
| `ingest/pipeline/<id>` | `ingest.put_pipeline` | an ingest pipeline definition |
| `search/pipeline/<id>` | `search_pipeline.put` | a search pipeline definition |
| `scripts/<id>` | `put_script` | a stored script |
| `snapshot/repositories/<name>` | `snapshot.create_repository` | a repository registration |
| `cluster/settings` | `cluster.put_settings` | persistent and transient cluster settings |
| `cluster/weighted_routing` | `cluster.put_weighted_routing` | shard routing weights |
| `cluster/uuid` | `GET /` on first call | the tenant's generated `cluster_uuid` |
| `tasks/index-management/<uuid>` | every index write | **the work queue — see below** |
| `tenants/<tenant-id>` **(root)** | a tenant's first write | **tenant discovery — see below** |
| `ingest/metadata-initialized` | first ingest pipeline write | marker, empty value |
| `search/metadata-initialized` | first search pipeline write | marker, empty value |
| `snapshot/repositories-initialized` | first repository write | marker, empty value |

The three `*-initialized` markers exist only to reproduce an OpenSearch quirk where a delete's response
changes once a metadata type has ever existed. **They are not state and the supervisor should ignore
them.** They are also why an empty value must stay distinguishable from an absent key.

## Documents

### `indices/<name>` — the important one

```json
{
  "index": "my-index",
  "uuid": "uzKxLWZu4nPSrTknEcDpoA",
  "creation_date": "1788969977933",
  "state": "close",
  "settings": {
    "index.number_of_replicas": "1",
    "index.number_of_shards": "3",
    "index.replication.type": "DOCUMENT",
    "index.verified_before_close": "true"
  },
  "mappings": { "properties": { "host": { "type": "keyword" } } }
}
```

Things worth knowing before writing a reconciler against this:

- **`settings` is flat and every value is a string.** `"3"`, not `3`; `"true"`, not `true`. Keys are always
  fully qualified with the `index.` prefix, whatever shape the client sent. The nested form clients see is
  a rendering applied on the way out.
- **`state` is `open` or `close`.** A closed index still has settings and mappings and still exists; it
  simply should not be serving. `index.verified_before_close` appears alongside and is OpenSearch's own
  bookkeeping.
- **`uuid` is the identity, not the name.** Names are reused. A supervisor that keys its actual-state
  bookkeeping on the name will confuse an index with its deleted predecessor.
- **`creation_date` is epoch millis in a string**, matching what OpenSearch stores.
- **Shard count is desired, not actual.** Nothing here says whether a shard exists anywhere. That is
  precisely the gap the supervisor closes.

### `aliases/<name>`

```json
{ "indices": { "my-index": { "is_write_index": true } } }
```

Keyed by alias, holding its members — the inverse of OpenSearch, where aliases live inside index metadata.
The reason is atomicity: the canonical zero-downtime swap (remove alias from `v1`, add to `v2`) becomes a
single-key compare-and-set. **An alias may name an index that does not exist yet**, or no longer does.

### `data_streams/<name>`

```json
{
  "name": "logs-app",
  "timestamp_field": "@timestamp",
  "generation": 1,
  "indices": [ { "index_name": ".ds-logs-app-000001", "index_uuid": "JqyK2fDEK5RrEZWGo4SPDA" } ]
}
```

Backing indices in order; **the last is the write index**. Each also exists as its own
`indices/.ds-…` document with `index.hidden: true`. `generation` only advances on rollover, which the
control plane does not implement yet, so today it is always 1.

### `tasks/index-management/<uuid>` — read this section twice

```json
{
  "task_id": "NmnqMpOCtk1I5aW_zVzSkA",
  "type": "create-index",
  "index": ".ds-logs-app-000001",
  "index_uuid": "JqyK2fDEK5RrEZWGo4SPDA",
  "state": "pending",
  "submitted_at": 1788969977936,
  "sequence": 2
}
```

`type` is one of `create-index`, `delete-index`, `update-mapping`, `update-settings`, `close-index`,
`open-index`.

**These records only ever accumulate.** The control plane writes one per index write and never revisits
it: nothing sets `state` to anything but `pending`, and nothing deletes a record. `cluster.pending_tasks`
reports the pile faithfully and it grows without bound. That is not an oversight — **completing and
reaping these tasks is the supervisor's half of the handoff**, and it is the single most load-bearing
sentence in this document.

`sequence` is per control plane process and restarts at zero, so it orders tasks within one instance and
means nothing across instances. `submitted_at` is millisecond resolution and ties are common, because one
wildcard request submits many tasks in the same millisecond. **Neither field is a reliable global
ordering.**

Two consequences for the supervisor:

1. **The task queue is a hint, not the source of truth.** A task can be lost (nothing guarantees the write
   landed), duplicated across retries, or arrive before the index document it refers to. The desired state
   is the `indices/` documents themselves; tasks tell you where to look first.
2. **Reconciliation must work with the queue empty.** A supervisor that only acts on tasks will never
   converge state that predates it, or state whose task it already consumed and then crashed before
   applying.

### `tenants/<tenant-id>` — the one key outside a tenant prefix

```json
{ "tenant": "acme", "registered_at": 1788969977933 }
```

**This is how the supervisor enumerates tenants**, and it is the only key the control plane writes at the
root of the store. `scanPrefix("tenants/")` is a small scan; the alternative — `scanPrefix("tenant/")` —
returns every key of every tenant, which is a full table scan to learn a list of names.

Four things about it are deliberate:

- **Written on a tenant's first *write*, not its first request.** An unrestricted tenant resolver accepts
  any well-formed id, so registering on request would let anyone grow the registry by inventing names. A
  tenant exists once something has been written for it.
- **Nothing ever deletes it.** A tenant whose keys are all gone may still be intended to exist, and the
  control plane cannot tell the difference. Removal is an operator action — so a registered tenant with no
  state is a finding for the supervisor to raise, not a conclusion to draw either way.
- **Best effort.** A failed registration is logged and the request succeeds. Discovery may lag by one write;
  the control plane will not 500 over a hint meant for another service.
- **`tenants/` and `tenant/` do not overlap.** `"tenants/acme".startsWith("tenant/")` is false, because the
  next character is `s` rather than `/`. They sort adjacently — every `tenant/` key precedes every
  `tenants/` key — so a scan written as `scanPrefix("tenant")` *without* the slash would pick up both.

### Smaller documents

```
templates/index/<name>       as the client sent it: index_patterns, composed_of, priority,
                             data_stream, template{settings,mappings,aliases}
templates/component/<name>   { "template": { settings, mappings, aliases } }
templates/legacy/<name>      as sent, plus "order"
ingest/pipeline/<id>         as sent: description, processors[]
search/pipeline/<id>         as sent: request_processors[], response_processors[], phase_results_processors[]
scripts/<id>                 { "lang": "painless", "source": "…" }
snapshot/repositories/<name> { "type": "fs", "settings": { … } }
cluster/settings             { "persistent": {…}, "transient": {…} }  — both always present, flat keys
cluster/weighted_routing     { "attribute": "zone", "weights": {"z1":1.0}, "version": 0 }
cluster/uuid                 the raw UUID string, not JSON
```

Template `settings` blocks are normalised the same way index settings are: flat, `index.`-prefixed,
string values.

## What is deliberately absent

Nothing here describes reality. There is no node list, no shard assignment, no health, and no heartbeat —
which is why `cluster.health`, `cluster.state` and `indices.get_data_stream`'s `status` field are all still
unimplemented in the control plane. **Everything the supervisor learns about what is actually running, it
learns from the data plane.** The control plane's contribution is entirely "what ought to be".

## Reading it

Use the same `KeyValueStore` the control plane uses — see `REQUIREMENTS.md` on sharing that code. Then:

```java
// which tenants exist at all
store.scanPrefix("tenants/");

// desired state for one tenant
store.scanPrefix("tenant/default/indices/");
store.scanPrefix("tenant/default/aliases/");
store.scanPrefix("tenant/default/tasks/index-management/");
```

`scanPrefix` is specified over **key prefixes, not path boundaries**, so `tenant/default/i` is a legal
prefix matching both `indices/` and anything else starting `i`. Prefixes ending in `/` are what you want.
