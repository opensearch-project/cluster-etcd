# The data plane contract

What a data plane node writes into the shared key/value store, and what the supervisor writes back for it
to read. Peer to [`KEY_LAYOUT.md`](KEY_LAYOUT.md), which is the same thing for the control plane.

This is `REQUIREMENTS.md` §3 — "defining it is this project's first real design task". It is a **proposal**,
not a dump of something that exists: no data plane speaks this yet. `KEY_LAYOUT.md` was generated by
exercising a real control plane; this file will only earn that status once a node implements it.

Designed independently of `../cluster-etcd`, which solves a similar problem with a different layout, and
then **checked against its plugin** — the only real data plane that has implemented anything like this.
None of its schema is borrowed. Several of its conclusions are, and one of its findings corrected a defect
here; the places where this document now differs deliberately say so. See *Checked against a real data
plane* at the end.

## Ground rules

**Nodes belong to pools, and a pool is the unit of ownership.** A node is not owned by a tenant. It belongs
to exactly one **pool**, and a pool may be *dedicated* (one large tenant, on nodes nothing else uses) or
*shared* (many small tenants). Node documents therefore live at the store root, outside any `tenant/`
prefix, and every per-index structure inside them is keyed by tenant first.

This is the decision with the widest blast radius in this document, and `DESIGN.md` §2 argues it. The short
version: exactly one supervisor owns a pool at a time, so **`nodes/assignment/<node-id>` has exactly one
writer by construction** — no lock, no coordination on the data path — and the supervisor fleet scales by
adding pools. A node shared between two pools would break that, which is why it cannot be.

**A node's pool comes from its own registration document**, which it takes from its deployment
configuration. `pools/nodes/<node-id>` overrides it when present; see below.

**One key segment decides the writer.** Under `nodes/`, the second segment says who may write:

| prefix | written by | read by |
|---|---|---|
| `nodes/registration/<node-id>` | the node | the supervisor |
| `nodes/heartbeat/<node-id>` | the node | the supervisor |
| `nodes/shards/<node-id>` | the node | the supervisor |
| `nodes/assignment/<node-id>` | the supervisor | that node only |

Nothing else writes under `nodes/`. A violation is detectable by reading a key, which is the point of
arranging it this way rather than grouping by node.

**Grouped by kind, not by node, deliberately.** The obvious layout is `nodes/<node-id>/heartbeat`. It is
worse, because the supervisor's hot path is "read every heartbeat, read almost no inventories", and
`scanPrefix` is a prefix scan with no way to skip a middle segment — under the obvious layout, one scan of
`nodes/` returns every shard inventory in the cluster on every pass. Grouping by kind makes the hot scan
exactly the hot data. The cost is that a node cannot watch one prefix covering all of its own keys; it does
not need to, because the only key it reads is its own assignment.

**`<node-id>` is the node's persistent identity**, the one that survives a restart — not its name and not
its ephemeral id. Names are reused and `KEY_LAYOUT.md` already warns what that does to bookkeeping keyed on
them. It must match `[A-Za-z0-9_-]{1,64}`, which the OpenSearch node id already does.

**Values are UTF-8 JSON.** The store does not know that; see `KEY_LAYOUT.md`.

## Three documents, split by how often they change

*(Plus a fourth, `nodes/heat/<id>`, which is **proposed rather than implemented** — see
[Heat, and why it is its own document](#heat-and-why-it-is-its-own-document). Nothing reads or writes it yet.)*

The split exists to satisfy R3.5 — *"a cluster of 200 nodes writing every few seconds is the store's
dominant write load, and both backends cap value size"*. One document holding everything would have to be
rewritten at the rate of its fastest-changing field and sized by its largest.

| document | changes | written |
|---|---|---|
| `nodes/registration/<id>` | on start, and if attributes change | once per process lifetime |
| `nodes/heartbeat/<id>` | continuously | every interval, default 5 s |
| `nodes/shards/<id>` | when a shard copy appears, changes state or goes | on change only |
| `nodes/heat/<id>` *(proposed)* | slowly, and on its own clock | every minute or slower |

200 nodes at 5 s is 40 writes/s of about a kilobyte. The inventory — the document that grows with shard
count — is off that path entirely.

### `nodes/registration/<node-id>`

Written once when the node starts, and rewritten only if something in it changes. A new `ephemeral_id`
means the process restarted.

```json
{
  "node_id": "pv1sDMfZRxSTMiW5VrbN9w",
  "ephemeral_id": "OYidGJ1ITdC2mMrZEW0BNQ",
  "name": "data-3",
  "pool": "shared-a",
  "roles": ["data", "coordinator"],
  "address": "10.0.3.14",
  "port": 9300,
  "version": "3.7.0",
  "attributes": { "zone": "z1", "rack": "r7" },
  "heartbeat_interval_millis": 5000,
  "registered_at": 1788969977933
}
```

- **`pool`** is the node declaring which pool it was deployed into, from its own configuration. It is the
  common case and it needs no operator write anywhere: deploy a node with `pool: shared-a` and the
  supervisor owning `shared-a` picks it up.

  **Precedence, stated once and binding on both sides:** if `pools/nodes/<node-id>` exists, its `pool` wins;
  otherwise this field is used; if neither exists the node is in no pool, is given no shards, and raises
  `NODE_UNPOOLED`. The override exists so a node can be moved between pools — taking its shard copies with
  it, which is the cheap form of migration (`DESIGN.md` §4) — without being redeployed. It is operator-owned
  precisely because a node must not be able to move itself into someone else's pool.

  A node whose declared pool has no `pools/definitions/<pool-id>` document is also `NODE_UNPOOLED`: a typo in
  a deployment config should strand one node visibly, not invent a pool.
- **`attributes`** are the awareness values weighted routing validates against, and projecting them is how
  the control plane finally gets its "discovered awareness values" check (R5.4). At most 32 entries, keys
  and values at most 128 characters — bounded because the control plane will render them in an API response.
- **`heartbeat_interval_millis`** is the node declaring its own cadence, and the supervisor derives that
  node's staleness threshold from it rather than from one global constant. A node that heartbeats every
  30 s is not dead at 40 s.
- **`roles`** decides what the node can be given. `data` takes shard copies; `coordinator` takes routing
  and no copies. A node may have both.

### `nodes/heartbeat/<node-id>`

The one hot key. Fixed shape, no unbounded field, and **the same size whether the node holds one shard copy
or ten thousand**.

```json
{
  "node_id": "pv1sDMfZRxSTMiW5VrbN9w",
  "ephemeral_id": "OYidGJ1ITdC2mMrZEW0BNQ",
  "timestamp": 1788969977663,
  "applied": { "assignment_version": 42, "outcome": "applied" },
  "shards_digest": "sha256:9f2c1b7e…",
  "shard_copies": 137,
  "capacity": {
    "disk_total_bytes": 994663170048,
    "disk_available_bytes": 856882249728,
    "heap_used_percent": 41,
    "cpu_used_percent": 5,
    "load_1m": 1.2
  }
}
```

- **`timestamp`** is the node's own clock, in epoch millis. It is diagnostic. **Liveness is not computed
  from it** — see below.
- **`ephemeral_id`** is echoed from the registration document so a restart is visible without re-reading
  registration on every pass.
- **`applied`** closes the loop on the assignment document: which `version` the node has acted on, and
  `outcome` of `applying`, `applied` or `failed`. A `failed` outcome may carry `detail`, capped at 512
  characters. **This is a hint, not a source of truth** — R2.1. The supervisor's model of what the node has
  is `nodes/shards/<id>`, always. The ack only makes a stuck or failing node visible sooner, and a
  supervisor that ignored the field entirely would still converge.
- **`shards_digest`** is the hex SHA-256 of the exact bytes the node last wrote to `nodes/shards/<id>`. It
  is how the supervisor avoids reading inventories that have not changed: it caches the digest of what it
  last read per node, and re-reads only on a mismatch. `shard_copies` is the count, which lets an
  inconsistency be spotted without the re-read.
- **`capacity`** is what allocation needs and nothing else. Absolute bytes, not percentages, because a
  decider comparing two nodes needs the denominator.

**Ordering requirement:** a node that has changed its inventory writes `nodes/shards/<id>` **before** the
heartbeat announcing the new digest. Then a mismatch always means "the heartbeat is behind the inventory",
which is safe to act on; the reverse would mean the supervisor chasing an inventory that does not exist yet.

**Size budget: 1 KiB typical, 4 KiB hard.** Nothing may be added to this document that scales with shard
count, index count or tenant count. That is the whole reason it exists.

### `nodes/shards/<node-id>`

Ground truth for actual state: what this node **has**, not what it was told (R3.2).

```json
{
  "node_id": "pv1sDMfZRxSTMiW5VrbN9w",
  "ephemeral_id": "OYidGJ1ITdC2mMrZEW0BNQ",
  "generated_at": 1788969977660,
  "tenants": {
    "acme": {
      "indices": {
        "uzKxLWZu4nPSrTknEcDpoA": {
          "name": "my-index",
          "config_revision": 3041,
          "shards": {
            "0": { "role": "PRIMARY", "state": "STARTED", "size_bytes": 4823012 },
            "1": { "role": "REPLICA", "state": "INITIALIZING" }
          }
        }
      }
    }
  }
}
```

- **Keyed by index uuid, with `name` alongside for humans.** `KEY_LAYOUT.md` is explicit that the uuid is
  the identity and a reconciler keyed on names will confuse an index with its deleted predecessor.
- **`config_revision`** is the store revision of the `tenant/<t>/indices/<name>` document whose settings and
  mappings this copy was built from — the "configuration version it has applied" of R3.2. Revisions are
  opaque and **comparable only for equality**; the node must not order them and neither will the supervisor.
- **`role` and `state` are separate dimensions**, and this is a correction: the first version of this
  document had one `state` field holding `PRIMARY`, `REPLICA`, `INITIALIZING` or `FAILED`. That cannot
  express *a primary that is still initializing*, and health cannot be computed without it —
  `active_primary_shards` counts copies that are both `PRIMARY` and `STARTED`, and an index whose primary
  exists but is initializing is red, not green. Conflated, those two were indistinguishable.
  - **`role`** is `PRIMARY`, `REPLICA` or `SEARCH_REPLICA`. The third was missing entirely and is a real
    OpenSearch role: a segment-replication replica that serves reads and never takes writes.
  - **`state`** is `INITIALIZING`, `STARTED` or `FAILED`. A `FAILED` copy may carry `reason`, capped at 512
    characters.
- **Two states OpenSearch has are deliberately absent, and the mapping is part of the contract** rather
  than left for each node implementer to invent:
  - **`RELOCATING`** — a move is reported as `STARTED` on the source and `INITIALIZING` on the target. An
    interrupted move then leaves two observations that mean what they say, rather than one state nobody
    owns and that every consumer has to special-case.
  - **`CLOSED` / `CLOSING`** — a closed index is reported as having no copies. `SUPERVISOR_KEYS.md` already
    says a closed index is green with no shards, matching OpenSearch, so the state would exist only to be
    filtered out again.

  Both mappings discard information the data plane has. They are decisions, not omissions.
- **`size_bytes`** is the most load-bearing field in this document, and more so than it first looked. It is
  what a disk-aware decider needs, and it is also the whole of the balancer's size signal — the thing
  OpenSearch's count-only balancer cannot see (`DESIGN.md` §14.2). Publishing it accurately is therefore worth
  real effort on the node's part: a pool where every shard reports roughly the same size is a pool that can only
  be balanced by count.

  Doc counts and per-shard statistics are still not here; they are an observability concern and would put an
  unbounded, fast-changing field into a document that is supposed to change only when placement does. **Heat**
  — the share of a node's search CPU one shard accounts for — is the field that would most improve balancing
  next, and it does not belong here for exactly that reason: it changes every few seconds. It wants a home on
  the heartbeat or a document of its own, capped to the busiest few shards.

  `size_bytes` is **omitted rather than zero** while a copy is initializing, because zero is a real size and
  would tell a decider the copy costs nothing. The supervisor fills the gap from the largest copy of the same
  shard elsewhere in the pool rather than guessing, so a node need not invent a figure it does not have.
- **`generated_at` means "when this inventory last changed", not "when it was last computed".** Found by
  implementing it: a node that stamps the current time every time it recomputes produces different bytes,
  and therefore a different digest, on every heartbeat — so the supervisor re-reads the inventory every
  pass and the document that scales with shard count is back on the hot path, which is the one thing this
  split exists to prevent. The node must leave the document untouched when the copies have not changed.
- **An empty inventory is still written.** "I have nothing" and "I have not yet said" are different facts,
  and only one of them is safe to place shards against. A node with no copies publishes
  `{"tenants":{}}` rather than leaving the key absent, so the supervisor has one code path instead of two.

**Size budget: 512 KiB hard**, well clear of ZooKeeper's 1 MiB default and etcd's 1.5 MiB. **Measured** at
93 bytes per copy with realistic index uuids and names: 5,000 copies serialise to 457 KiB, which is 89% of
the budget, and the ceiling is about 5,600 copies per node. Splitting role from state cost 39 bytes per
copy — 54 to 93 — and that is the price of being able to compute health correctly. It is tighter than is
comfortable and worth knowing: a real OpenSearch node holds hundreds of shards rather than thousands, so
the ceiling is far above practice, but there is no headroom left for another per-copy field. A node that
would exceed the budget must write nothing and report `outcome: failed` — a truncated inventory is worse
than a missing one, because the supervisor would read it as "those copies are gone" and start replacing
shards that exist.

## Heat, and why it is its own document

**Status: proposed. Nothing implements this.** It is written down now because the balancer's signal interface
was built to take it (`DESIGN.md` §14.2) and because the shape has a few decisions in it that are much cheaper
to argue about before there is code.

Heat is the share of a node's search work that one shard is responsible for. It is the signal that turns
balancing from "spread the bytes evenly" into "spread the *work* evenly", and it is the one thing neither
`size_bytes` nor shard count can approximate: a 200 GiB archive shard nobody queries and a 200 GiB shard
serving every request look identical to every signal that exists today.

### The controlling constraint: do not act faster than you can measure

Moving a 20 GiB shard takes minutes. A signal that fluctuates over seconds will therefore reliably provoke
moves that finish after the condition they were responding to has gone — the balancer spends real bandwidth
chasing spikes and arrives late every time. So the signal has to be smoothed over a window several times
longer than a move takes, and only *consistently* hot shards should ever be separated.

Everything else in this section follows from that.

### The smoothing belongs to the node, not the supervisor

This is the decision that matters most, and it is why heat is a separate document rather than a field on the
heartbeat.

If the node publishes instantaneous values, the supervisor has to smooth them across passes — which means
keeping a per-shard exponential average in supervisor memory. That breaks two things this design has been
careful about everywhere else:

- **R2.1.** Reconciliation is a pure function of observed state. The only memory kept anywhere —
  `RevisionSilence`, `FindingAges` — is documented as having to grant full grace after a restart, precisely
  because remembered state is a liability.
- **Lease handoff.** A pool moving to another supervisor would arrive with no heat history at all, and would
  either balance blind or need a warm-up window during which its decisions are wrong. That is an operational
  cliff for a feature whose whole justification is being a background nicety.

If the **node** publishes an already-smoothed figure, both problems disappear. The smoothed value is part of
observed state, so it survives supervisor restarts and lease moves, and the supervisor stays a pure function of
what it reads. The node can trivially afford it: one exponential average per shard, over data it already has.

And it does double duty, which is the actual answer to the spike problem. **The smoothing window *is* the
patience.** With a ten-minute half-life, a thirty-second spike moves the average by a few percent and cannot
clear `MoveThresholdDecider`'s margin. The noise filter and the hysteresis become the same mechanism, and no
separate spike detection is needed. That only works if the node smooths.

### Absolute work, not a share of the node

The obvious unit is "percentage of this node's CPU spent on searching this shard", and it is the wrong one,
because a share of the node cannot be compared *between* nodes. A node 90% busy with one shard accounting for
half of that, and a node 10% busy with one shard accounting for half of that, publish the same number for a
nine-fold difference in real work — and the load model's entire job is comparing nodes.

The right unit is **CPU-seconds per second attributable to the shard**: the average number of cores busy on it.
That is comparable across nodes, sums to something meaningful per node, and leaves capacity normalisation as a
separate step the load model can apply from the heartbeat's `Capacity` if the hardware is heterogeneous. It is
the same split `DiskThresholdDecider` already makes by reading a fraction rather than free bytes: how much work
and how much capacity are two facts, and merging them early throws one away.

### Sparse, and honest about being sparse

Heat only carries information when some shards are distinctly hotter than others; a node whose shards are all
equally warm has nothing to say and should say nothing. So a node publishes only shards above some share of its
own total, capped at a fixed count, and `shards_omitted` records how many it left out — which is what
distinguishes *"nothing stood out"* from *"this node does not measure heat"*.

That distinction has a consequence for the supervisor, and it is the one thing about heat that could go badly
wrong. **A node that does not publish heat looks cold, and a cold node attracts work.** Since heat will be
optional across node versions for a long time, partial data is worse than none: the rule must be that the heat
signal is used only if *every* placeable node in the pool publishes it, and otherwise its importance drops to
zero for that pool. Same reasoning as `size_bytes` being omitted rather than zero — absent must mean *unknown*,
never *none*.

### Proposed shape

```json
{
  "node_id": "sQ3xLWZu4nPSrTknEcDpoA",
  "ephemeral_id": "eph-91c2",
  "generated_at": 1757000000000,
  "half_life_millis": 600000,
  "node_search_cores": 1.42,
  "shards": [
    { "tenant": "acme", "index_uuid": "uzKxLWZu4nPSrTknEcDpoA", "shard": 3, "search_cores": 0.84 },
    { "tenant": "acme", "index_uuid": "uzKxLWZu4nPSrTknEcDpoA", "shard": 7, "search_cores": 0.31 }
  ],
  "shards_omitted": 122
}
```

- **`half_life_millis`** is the node declaring its own smoothing window, exactly as
  `heartbeat_interval_millis` declares its cadence. Self-describing for a reason: the supervisor should
  **refuse a window too short to act on** rather than assume one. Balancing on a ten-second average is worse
  than not balancing.
- **`node_search_cores`** is the node's own total, which lets the supervisor tell "this shard is 60% of a busy
  node" from "60% of an idle one" without needing every shard listed.
- **`shards`** is a list rather than the inventory's nested map, because it is a *ranking* — sorted hottest
  first, truncated — and nesting by tenant and index would make the truncation boundary arbitrary.
- **`ephemeral_id`** so a document left by a previous process is recognisable, as everywhere else.
- Written on its own clock, not the heartbeat's. A minute is frequent enough for a ten-minute average; slower
  is fine. The supervisor reads it lazily, since rebalancing only runs on a pass with nothing else to do
  (`DESIGN.md` §14.6) — so heat is needed exactly when the supervisor is otherwise idle.

### Why not on the heartbeat

Simpler, and that is a real argument. Against it:

- The heartbeat is read **every pass, by definition** — it is the liveness signal. Heat in it means paying for
  heat bytes on every node on every pass, forever, on the one document guaranteed to be hot.
- It is a variable-length list on a document that is deliberately small and fixed-shape, with a 4 KiB budget.
- The cadences are genuinely different and should be tunable apart: liveness wants seconds, heat wants
  minutes. Sharing a document would force whichever is wrong for one of them.

## What the supervisor writes back

### `nodes/assignment/<node-id>`

The node's full desired state. Written only when it changes.

```json
{
  "version": 42,
  "pool": "shared-a",
  "epoch": 7,
  "node_id": "pv1sDMfZRxSTMiW5VrbN9w",
  "generated_at": 1788969977500,
  "tenants": {
    "acme": {
      "role": "data",
      "indices": {
        "uzKxLWZu4nPSrTknEcDpoA": {
          "name": "my-index",
          "config_revision": 3041,
          "shards": { "0": "PRIMARY", "1": "REPLICA" }
        }
      }
    },
    "globex": { "role": "coordinator" }
  }
}
```

- **It is the complete desired set, never a delta.** A shard copy the node holds and this document does not
  name must be removed. This is R2.1 pushed all the way down: a data plane that applied deltas would have
  the same edge-triggered bug one layer lower, and it would be harder to see.
- **An absent assignment is not an empty one.** Added after implementing the node, which had to guess:
  read as "the complete desired set is empty", a missing key means *drop every shard you hold* — and a
  supervisor that has not written one yet, a pool between owners, and a lost key all look exactly like
  that. **Absent means no instruction**: the node keeps what it has and keeps reporting the last version it
  applied. Only an assignment that is present and names nothing drops everything.
- **An assignment names a role, never a state.** The values are `PRIMARY`, `REPLICA` or `SEARCH_REPLICA`.
  A state is something a node reports about how it is getting on; asking for one would be asking for
  something the node cannot converge to, so the diff would never empty. Rejected when the document is
  built rather than discovered in a reconciliation loop.
- **`version`** is monotonic **per node** and means nothing across nodes. The node echoes it in
  `applied.assignment_version`. **Versions start at 1**, because 0 is the heartbeat's "nothing applied
  yet" and an assignment numbered 0 would be indistinguishable from never having been given one.
- **`pool` and `epoch`** identify who wrote this and under what leadership: the pool the writer believed
  this node was in, and that pool's lease epoch. The node ignores both. They exist so that an assignment
  written by a supervisor that had already lost the pool is identifiable after the fact — and so that a node
  observed to be moving between pools can be told apart from one being fought over, which look identical
  from the shard contents alone.
- **The single writer is the owner of this node's pool**, which is one supervisor by construction
  (`DESIGN.md` §2). Nothing in this document is merged from multiple sources, and no supervisor ever
  compare-and-sets against another's write on the normal path.
- **`config_revision`** tells the node which revision of the index document to build against. If the node
  reads `tenant/acme/indices/my-index` and finds a different revision, the assignment is stale by one pass
  and it should apply what it read — the supervisor will re-issue.
- **The node must check the index document's `uuid` against the uuid its assignment named**, and treat a
  mismatch as "this index is not present yet" rather than as configuration to apply. The assignment
  identifies an index by uuid but the index document is keyed by *name*, so an index deleted and recreated
  under the same name gives the node a perfectly valid document describing a different index. Both halves
  read cleanly; only the pair is wrong. This is the one torn read in the contract that a later pass would
  not correct, because the node would have built the shard already.
- **A tenant entry with `role: coordinator`** and no `indices` means "serve queries for this tenant, hold no
  data". Where the coordinator gets the routing table it needs is the next section.
- **Size budget: 512 KiB hard**, same reasoning. If a node's assignment would exceed it the supervisor
  writes nothing and raises a finding; it does not truncate. The escape hatch, if this is ever hit in
  practice, is to split per tenant — `nodes/assignment/<node-id>/<tenant>` — which the layout permits
  without moving anything else.

### Routing is not here, and neither is peer wiring

A coordinator needs to know where every shard of its tenants lives. So, under document replication, does a
data node: a replica must know which node holds its primary, and a primary must know its replicas in order
to fan writes out to them.

None of that goes in the assignment. The table is identical for every reader, so putting it in each node's
assignment would store it N times and rewrite all N copies whenever one shard moved — and with peer
endpoints inlined it would also roughly triple the per-copy cost of a document that is already at 89% of
its budget.

It lives instead at `tenant/<t>/status/indices/<index-uuid>`, one document per index, written by the
supervisor. That single projection serves four readers: `cluster.health`, `cluster.state`, coordinator
routing, and docrep peer resolution. Node addresses come from `tenant/<t>/status/nodes/<node-id>`, which
exists for `cluster.state` and already carries `address` and `port`. See
[`SUPERVISOR_KEYS.md`](SUPERVISOR_KEYS.md).

So a node reads its own `nodes/assignment/<id>` to learn what it should hold and which tenants it serves,
and then — only if it needs peers — the two status projections for those tenants.

### Peer resolution, and why it is not what `cluster-etcd` does

`cluster-etcd` puts peer node *names* in the goal state (`primary_node` on a replica, `replica_nodes` on a
primary) and then resolves each name to an address by **reading that node's heartbeat**. Two reasons not to
copy it:

- **It makes every data node a reader of every other data node's document.** That couples the data plane to
  the heartbeat schema, adds a read fan-out on every goal-state change, and gives a document whose single
  writer is one node a second class of reader that its author never has to think about. Reading a
  supervisor-owned projection instead keeps one writer and one documented schema.
- **Names are reused; ids are not.** `KEY_LAYOUT.md` is explicit about this, and peer identity resolved by
  name will eventually point at a node's successor.

**Whether an index needs peers at all is a property of the index, not of the assignment.** It comes from
`index.replication.type` in `tenant/<t>/indices/<name>` — `DOCUMENT` or `SEGMENT`, already present in the
control plane's index document. A segment-replication copy pulls from the remote store and resolves no
peers, which is why the bare role string is sufficient for it.

**Convergence is level-triggered here too, and this is the part worth getting right.** When the supervisor
places a primary and a replica in the same pass, the replica will read the projection before the primary is
serving. It must then stay `INITIALIZING` and try again, not fail. Which means the projection has to list
copies that are not yet started — a projection filtered to `STARTED` only would deadlock: the replica could
never see the primary it is waiting for. `tenant/<t>/status/indices/<uuid>` therefore lists every observed
copy with its role and state, and the replica waits for a primary whose state is `STARTED`.

The corresponding obligation on the supervisor is to place a shard's primary before its replicas, since a
replica placed first cannot converge until one exists. That is a planning rule, and it is open question 2.

## Forward compatibility

Added after implementing both sides. A rolling upgrade means one side is routinely newer than the other, so
this is the normal case rather than the exceptional one.

- **Unknown fields are ignored.** Failing the parse loses the whole document, and for an inventory that
  reads as "this node has no shards" — the most destructive possible response to an unrecognised field.
- **An unknown enum value becomes a sentinel, and the sentinel is never counted as healthy.** An
  unrecognised shard state is neither serving (which would have the supervisor believe a shard is served
  when it is not) nor absent (which would have it place a duplicate). It is "something is there and I
  cannot say what", which is a finding for a human.
- **A document carrying a sentinel cannot be written back.** Reading one is required; re-serialising it
  would fabricate a document claiming a value no peer ever reported.

One implementation note, because it cost an afternoon and will cost the next person the same: with Jackson,
this cannot be done with `@JsonValue` on the enum. Jackson builds an enum's *deserializer* by calling that
accessor on every constant to construct its lookup table, so a sentinel that throws on write also breaks
reading — defeating the one thing it exists for. The guard belongs on a registered serializer, which runs
only when something genuinely tries to write.

## Liveness

R3.3 says a node whose heartbeat is older than a threshold is presumed gone, and that getting the threshold
wrong in either direction is how these systems cause outages.

**Refinement, stated as a decision:** staleness is measured from **when the supervisor last observed that
key's revision change**, not by subtracting the node's `timestamp` from the supervisor's clock. Two clocks
that disagree by a minute would otherwise either kill a healthy cluster or keep a dead node's shards
unrecovered, and clock skew is not a rare condition. The `timestamp` field stays, for two things it is
genuinely good at: showing an operator how far behind a node is, and catching a node whose own clock has
stopped while it keeps writing.

This works because **the heartbeat value changes on every write** — the timestamp guarantees it — so the
revision always advances. A fixed-content heartbeat would break this, which is why `timestamp` is required
rather than optional.

Consequences, all of which have to be built:

- **"Last observed change" is in memory**, and R2.3 forbids depending on in-memory state. Losing it is
  benign if a restarted supervisor grants every node a **full staleness window before declaring anything
  dead**. That startup grace period is not optional; without it, a supervisor restart evicts the cluster.
- **Detection cannot be short-cut, and this is easy to get wrong.** A supervisor that has just read a
  heartbeat revision for the first time must watch it sit still for the whole threshold, however long ago
  the node actually wrote it — inferring age from the node's own timestamp is the thing this scheme exists
  to avoid. So worst-case detection is the threshold plus one pass interval, and advancing a clock does not
  accelerate it. Obvious in hindsight; it invalidated a test that jumped the clock and expected an immediate
  verdict.
- **The grace period for a node with a registration and no heartbeat runs from when the supervisor first saw
  that node**, not from when the supervisor started. The latter meant a supervisor running for an hour
  condemned every newly registered node on sight, before it could write a first heartbeat.
- **The threshold is per node**, derived as `max(floor, multiplier × heartbeat_interval_millis)` from that
  node's registration. Default multiplier 6, floor 20 s — both configurable, and the **effective** value
  per node is published (R3.3 requires it be observable, and this is exactly the number an operator will
  want during an incident).
- A node that is stale is **not** immediately treated as having no shards. It is a finding
  (`NODE_STALE`) that becomes `NODE_LOST` after a second, longer threshold. The gap between them is the
  system's tolerance for a GC pause or a network blip.

## Torn state, enumerated

R2.5 says torn state is normal and must never be treated as corruption. Four documents written by two
services with no cross-key transaction produce exactly these tears, and each needs a decided answer rather
than a retry loop that happens to work.

| observed | means | supervisor does |
|---|---|---|
| heartbeat, no registration | heartbeat landed first, or registration was lost | keep existing copies, place nothing new; finding `NODE_UNREGISTERED` |
| registration, no heartbeat | node is starting | grace period; not stale, not lost |
| `shards_digest` ≠ digest of the inventory read | inventory write not yet visible | use what was read; re-read next pass |
| `applied.assignment_version` < assignment `version` | node has not caught up | normal; a finding only after N passes |
| `applied.assignment_version` > assignment `version` | the supervisor read a stale assignment, or another supervisor is writing | verify the lease, discard the pass, recompute (R6.3) |
| `ephemeral_id` changed | node restarted | discard cached inventory and every ack; re-read |
| heartbeat and inventory disagree on `ephemeral_id` | the pair straddles a restart | **prefer the inventory** and treat the ack as void. A node writes registration, then inventory, then heartbeat, so within one process the inventory is never the older of the two; across a restart the previous process's heartbeat can outlive it |
| the assignment's `pool` ≠ the node's current pool | written by the pool's previous owner, or the node has just been moved | the new owner rewrites it; the old owner must stop, and the `epoch` says which is which |
| a node in my pool holds copies of a tenant bound elsewhere | a rebind in progress, or an abandoned one | `FOREIGN_COPY`; remove only once the binding shows no `moving_to` and the finding has aged |
| inventory names an index uuid absent from desired state | index deleted — **or** desired state is torn | finding `ORPHANED_COPY`; **do not delete until it has been observed for K consecutive passes** |

The last row is the one that matters. An index document that has not yet landed and an index that was
deleted look identical, and one of the two readings destroys data. Waiting K passes costs disk on a deleted
index and costs nothing else; not waiting costs the shard.

## Checked against a real data plane

`../cluster-etcd`'s plugin is the only implementation of anything like this contract that has actually run,
so it was read after `fake-node` was written, specifically to find out where a real node would push back.
Its key layout is not a model — it is one document per node holding everything — but its *behaviour* is
evidence, and reading it changed this document in four places.

**What it confirms.** A node genuinely has all of the identity this contract assumes: OpenSearch gives it a
persistent node id and an `ephemeralId` that changes on restart, so restart detection needs nothing
invented. It advertises its own heartbeat interval, as here. `INITIALIZING` is directly observable from the
routing table. And it reads index settings and mappings from the store itself rather than having them
inlined into its assignment — which is open question 1's "the node reads", implemented and working.

**What it corrected.** Its shard reporting carries `role` and `state` as separate fields, plus a third role,
`search_replica`. This document had them collapsed into one enum and was wrong; see above.

**What it warns about.** Its heartbeat is a single document, written every five seconds, carrying the
node's capacity *and* its whole routing view *and* shard-level index statistics. Note what that routing view
is and is not: in a clusterless model a node's synthesized cluster state holds only what it was told about,
so a data node reports its own shards plus, under document replication, the immediate peers of those
shards — not a global picture. It is still the shape R3.5 warns against, because the document is rewritten
every five seconds and grows with the number of shards on the node, which is precisely what the split here
takes off the hot path. But it is bounded by the node's own footprint rather than by the cluster's, and
saying otherwise would overstate the case.

The sharper edge is on coordinators. A coordinator's local view *is* its tenant's placement set, so its
heartbeat carries a table that grows with the tenant rather than with the coordinator — and every
coordinator of that tenant carries its own copy, rewritten on the same five-second timer. That is the same
duplication this contract avoids by sending coordinators to a single `tenant/<t>/status/indices/<uuid>`
projection instead of pushing a routing table into each of them.

**Where it does the opposite, deliberately.** Deleting a node's goal state resets that node to an empty
cluster state — it drops everything. But a goal state that is simply *absent at startup* causes no action
at all. So the same store contents mean two different things depending on whether the node saw the
transition, which is edge-triggering (R2.1) one layer below the supervisor: restart a node and it behaves
differently from one that stayed up. This contract's "absent means no instruction, present-and-empty means
drop everything" is level-triggered and gives one answer to one state of the store. The cost is that an
operator can no longer say "drop everything" by deleting a key; they have to write an empty assignment.

**One thing it needs that this contract cannot yet express**, and it is the open question below rather than
a correction, because it is a design fork rather than an oversight — see question 2.

**One thing worth not copying.** A restarting node recovers its own allocation ids by reading back the
heartbeat it previously published, using the store as its own memory. Allocation ids are on the node's
local disk; a store round-trip makes them lossable in a way they otherwise would not be.

## Checked against the real plugin

`../opensearch-data-plane` is the first implementation of this document inside a running OpenSearch node.
Its publishing half — registration, heartbeat, inventory — is built and passing, against OpenSearch 3.9.
The two implementations now share a conformance suite (`fake-node/src/testFixtures`, `NodeContractTests`),
which is how they stay one format: the plugin re-implements the codec on XContent because the server
exposes Jackson's streaming API and not databind, so nothing but that suite connects them.

**Five things it found. Four are silences in this document rather than errors.**

1. **`SPLITTING` is a shard state this document does not enumerate.** OpenSearch 3.x has an in-place shard
   split, so `ShardRoutingState` has five values rather than the four assumed above. The plugin maps it to
   `STARTED`, which matches the server's own `active()` — that counts started, relocating and splitting
   alike — and the copy is on disk and serving throughout.

   **Low priority, and recorded mainly so the mapping is not left to chance.** In-place live shard splitting
   is not the approach this design takes: pull-based ingestion makes a split a matter of standing up a new
   index with the new shard layout, restoring from snapshot, deleting the out-of-shard documents and
   resuming from the checkpoint in the shard snapshot — so `SPLITTING` should never appear in a pool this
   system owns. Handling it costs one enum case and nothing else. Found by the mapping being written as an
   exhaustive switch, which made a new enum constant a compile error; a chain of `if`s would have silently
   reported a splitting shard as whatever the last branch said.

2. **`FAILED` is not observable from the routing table, so a node cannot report it the way it reports the
   other two.** A shard that fails in OpenSearch is *removed* from the routing table rather than marked in
   it — there is no `FAILED` routing state. So a node's inventory can only carry `FAILED` if the node
   keeps its own record of the failure alongside the routing table, which is a real obligation this
   document places on an implementer without saying so. Not yet exercised: it lands with the applier.
   **Proposed: say that `FAILED` is the node's own bookkeeping, not a projection of server state.**

3. **When the inventory cannot be written, the document does not say what the heartbeat should carry.**
   D3.6 says "write nothing and report `outcome: failed`", which leaves `shards_digest` and
   `shard_copies` undecided, and they are the fields the supervisor acts on. The plugin's answer:
   **the digest keeps describing the bytes last actually written** — that is what the field means, and any
   other value would send the supervisor chasing a document that does not exist — while **`shard_copies`
   reports the true current count**. The two then disagree, and that disagreement is precisely the
   documented signal that a node's inventory is behind. **Proposed: state this, because the alternative
   (blanking the digest) reads as "this node has never written an inventory" and is very easy to write.**

4. **`registered_at` on a rewritten registration.** The document says the registration is rewritten when an
   attribute changes and does not say whether the timestamp moves. The plugin keeps the original: a node
   that has been up for a day should not look as though it had just arrived because somebody relabelled
   its rack. **Proposed: state it either way; the field is otherwise ambiguous during exactly the incident
   where an operator is reading it.**

5. **A node has one address here and two in reality.** `registration` carries `address` and `port`, which
   the plugin fills from the transport address — the right answer for a coordinator resolving a data node,
   and what `tenant/<t>/status/nodes/<id>` projects onward. But OpenSearch nodes also have an HTTP
   endpoint, and `cluster.state`'s node list carries both. **So the control plane cannot render
   `http_address` for a node, and nothing in this layout can currently tell it one.** Not a defect in the
   data path; a gap in what the projections can serve, and cheaper to decide now than after something
   depends on the shape.

**One thing it confirms with a caveat.** `heartbeat_interval_millis` is the node's own declaration and the
plugin honours it, but a node scheduling at a *fixed delay* — which is what it should do, since a fixed
rate against a slow store queues passes that were stale when they were queued — writes every
`interval + pass duration`. The declared figure is therefore a lower bound rather than the period. Harmless
at the default multiplier of six, and worth knowing before anyone tightens it.

## Open questions

0. **Resolved by implementing it** — recorded here so the list stays honest rather than looking untouched.
   `generated_at` means "last changed"; an absent assignment is not an empty one; an empty inventory is
   still published; only serving states are assignable; assignment versions start at 1. Each was a silence
   in this document that `fake-node` had to guess at, and each is now stated above.

1. **Does the node need to be told its tenants' index documents, or does it find them?** As written it
   reads `tenant/<t>/indices/<name>` itself, which means the data plane needs the tenant prefix convention
   and a store client. The alternative — inlining settings and mappings into the assignment — removes that
   dependency and makes the assignment document large and hot. Current answer: the node reads.
   **`fake-node` does neither** — it echoes the `config_revision` the assignment gave it, which is enough
   to exercise the seam and is exactly the shortcut a real node cannot take.
2. **Ordering primary before replica** is now a planning rule the supervisor owes the data plane, and it is
   not yet written. See *Peer resolution* above for why: a docrep replica cannot make progress until a
   primary exists to replicate from, so a plan that places replicas first converges only by accident.
   `DESIGN.md` §6 has the finding; the rule itself belongs in the planner, at milestone 5.
3. **Whether `FAILED` copies count as present** for allocation. They occupy disk and cannot serve. Leaning:
   present for capacity, absent for health and routing.
4. **Cross-pool recovery.** If a shard is ever to be copied from a node in one pool to a node in another —
   which is one of the sketched answers to rebinding a tenant (`DESIGN.md` §4) — the recovery source is in a
   part of the keyspace the receiving node's supervisor does not own. Either the assignment names the source
   explicitly, or the whole idea is dropped in favour of moving nodes and snapshot/restore. This is open
   question 2 with the stakes raised, and the two should be answered together.
